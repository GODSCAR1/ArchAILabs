# /graphify

Turn any folder of files into a navigable knowledge graph with community detection, an honest audit trail, and three outputs: interactive HTML, GraphRAG-ready JSON, and a plain-language GRAPH_REPORT.md.

## Usage

```
/graphify                                             # full pipeline on current directory (HTML viz; add --obsidian for a vault)
/graphify <path>                                      # full pipeline on specific path
/graphify https://github.com/<owner>/<repo>           # clone repo then run full pipeline on it
/graphify https://github.com/<owner>/<repo> --branch <branch>  # clone a specific branch
/graphify <url1> <url2> ...                           # clone multiple repos, build each, merge into one cross-repo graph
/graphify <path> --mode deep                          # thorough extraction, richer INFERRED edges
/graphify <path> --update                             # incremental - re-extract only new/changed files
/graphify <path> --directed                            # build directed graph (preserves edge direction: source→target)
/graphify <path> --whisper-model medium                # use a larger Whisper model for better transcription accuracy
/graphify <path> --cluster-only                       # rerun clustering on existing graph
/graphify <path> --no-viz                             # skip visualization, just report + JSON
/graphify <path> --html                               # (HTML is generated by default - this flag is a no-op)
/graphify <path> --svg                                # also export graph.svg (embeds in Notion, GitHub)
/graphify <path> --graphml                            # export graph.graphml (Gephi, yEd)
/graphify <path> --neo4j                              # generate graphify-out/cypher.txt for Neo4j
/graphify <path> --neo4j-push bolt://localhost:7687   # push directly to Neo4j
/graphify <path> --falkordb                           # generate graphify-out/cypher.txt for FalkorDB
/graphify <path> --falkordb-push falkordb://localhost:6379   # push directly to FalkorDB
/graphify <path> --mcp                                # start MCP stdio server for agent access
/graphify <path> --watch                              # watch folder, auto-rebuild on code changes (no LLM needed)
/graphify <path> --wiki                               # build agent-crawlable wiki (index.md + one article per community)
/graphify <path> --obsidian --obsidian-dir ~/vaults/my-project  # write vault to custom path (e.g. existing vault)
/graphify add <url>                                   # fetch URL, save to ./raw, update graph
/graphify add <url> --author "Name"                   # tag who wrote it
/graphify add <url> --contributor "Name"              # tag who added it to the corpus
/graphify query "<question>"                          # BFS traversal - broad context
/graphify query "<question>" --dfs                    # DFS - trace a specific path
/graphify query "<question>" --budget 1500            # cap answer at N tokens
/graphify path "AuthModule" "Database"                # shortest path between two concepts
/graphify explain "SwinTransformer"                   # plain-language explanation of a node
```

232: Hallazgos del paso 5, usados como evidencias en los ADR 0013-0015:
233: 
234: 1. **Reserva lógica frente a apartado físico.** El sistema reserva al crear el pedido (`CreateOrderService` → `InventoryFacade.reserve`), antes de cobrar. 239: 6. **El cupón no llega al checkout:** `Coupon` vive en `pricing`, pero `PlaceOrderCommand` no lo transporta.
240: 7. **Catálogo lee la tabla `stock` de Inventario** con SQL (`CatalogStockProjectionJob`: `select product_id, available from stock`). Es una dependencia oculta Inventario → Catálogo que no sale en los imports y que ArchUnit no ve.

2:

7:

10:   Hubo tres términos que significaban dos cosas según quién hablara: *reserva* frente a *apartado*,
11:   *cobro anulado* frente a *reembolso* y *cliente* frente a *cuenta de usuario*.

16: - Los hotspots se concentran en el pedido (H1, H4, H5, H7) y en el precio (H8, H9).
17: 
18: ## Decisión
19:

21:    Pedidos (`ordering`), Precios y promociones (`pricing`), Catálogo (`catalog`), Inventario
22:    (`inventory`), Identidad y acceso (`identity`), Pagos y riesgo (dentro de `ordering` hasta la
23:    Sección 35), y Envíos, Devoluciones, Facturación y Atención al cliente, todavía sin módulo.
24: 2. **Core:** Pedidos y Precios y promociones. **Generic:** Identidad, Facturación y la pasarela de Pagos.
25:    El resto son **supporting**.

27:    comparten Precios y Pedidos. `Coupon`, `VolumeDiscount` y el resto de `pricing` no forman parte de él.

29: 5. Cada término del glosario pertenece a un solo contexto. Un concepto que parece de dos son dos términos.

1: # ADR 0014 — Integración entre contextos: consultas por puertos, efectos por eventos
2: 
3: - Estado: aceptado (lab S19, 2026-11-24)
4: - Evidencias: `docs/domain/event-storming.md` (tablero frente a código), `docs/domain/context-map.md`
5: - Relacionados: ADR 0012 (hexagonal), ADR 0013 (límites), ADR 0015 (reserva síncrona)
6: 
7: ## Contexto
8: 
9: - Hay una flecha en los dos sentidos entre Catálogo y Pedidos. Catálogo da los precios (consulta), pero la
10:   disponibilidad la empuja `ordering`, llamando a `catalog.api.CatalogStockProjection` desde su relay:
11:   Pedidos decide cuándo cambia el Catálogo.
12: - `CatalogStockProjectionJob` (catalog) lee la tabla `stock` de Inventario por SQL. Es una dependencia que no
13:   sale en los imports y que `ModuleBoundariesTest` no ve.
14: - La cancelación ya se integra por evento: `OrderCancelled` → `OrderCancelledListener` → `InventoryFacade.release`.
15: - La reserva al crear el pedido es síncrona porque el negocio exige que un pedido no nazca sin stock (ADR 0015).
16: - En la Sección 39 los contextos pasarán a comunicarse con eventos entre servicios.
17: 
18: ## Decisión
19: 
20: 1. **Consultas síncronas:** solo a través del paquete publicado del contexto dueño (`<modulo>.api`, o el
21:    shared kernel de `pricing`), y solo desde `infrastructure/adapters/out/<modulo>` o `config` del consumidor.
22: 2. **Efectos en otro contexto:** por eventos de dominio que publica el contexto donde ocurre el cambio. El
23:    contexto afectado reacciona al evento. Ningún contexto manda una orden a otro para cambiar su estado.
24: 3. **Prohibido** acceder a tablas, colecciones, entidades JPA, documentos Mongo o repositorios de otro contexto.
25: 4. Excepciones catalogadas (solo estas):
26:    - `InventoryFacade.reserve`: efecto síncrono por decisión de negocio (ADR 0015).
27:    - `CatalogStockProjection` llamado desde `ordering`: deuda, pasa a evento en la Sección 39.
28:    - Lectura de la tabla `stock` desde `catalog`: deuda, misma corrección.
29: 
30: **Verificación:** `ModuleBoundariesTest.modules_only_use_the_published_api_of_other_modules` (punto 1),
31: `ContextMapTest.cross_context_calls_only_use_catalogued_ports` (lista cerrada de puertos, puntos 1 y 4),
32: `ContextMapTest.no_module_touches_another_modules_persistence` (punto 3, tipos) y `TableOwnershipTest`
33: (punto 3, SQL: cada tabla tiene un módulo dueño, y la única excepción es `stock` desde `catalog`).
34: 
35: ## Consecuencias
36: 
37: - ✅ El acoplamiento entre contextos queda en una lista cerrada que se revisa en cada PR.
38: - ✅ Llegar a la Sección 39 es sustituir tres excepciones conocidas, no buscar dependencias ocultas.
39: - ❌ Los efectos por evento son eventualmente consistentes: la disponibilidad del catálogo va por detrás del
40:   pedido (hoy, hasta el intervalo del relay).
41: - ❌ Cada puerto nuevo entre contextos obliga a editar la lista de `ContextMapTest` y este mapa, lo que
42:   añade fricción a propósito.
43: - ❌ `TableOwnershipTest` busca nombres de tabla en el código fuente: el SQL dinámico se le escapa y un
44:   nombre de tabla en un comentario da un falso positivo.
45: 
46: ## Alternativas
47: 
48: - Todo síncrono por fachadas: descartada. Ata la disponibilidad de un contexto a la del otro y empuja hacia ciclos.
49: - Base de datos compartida con vistas por contexto: descartada. Esconde el acoplamiento en el esquema.
50: - Todo por eventos, incluida la reserva: descartada. El pedido podría nacer sin stock (ADR 0015).

## Resumen

Hoy, **confirmar la compra inicia un pago sobre un pedido que ya existe y cuyo stock ya se reservó**. Pedidos fija el importe, solicita la autorización a la pasarela y, si esta la concede, registra el pedido como `PAID` y genera `OrderConfirmed`. La actualización de la disponibilidad visible en Catálogo ocurre después, de forma diferida. [Fuentes: `docs/domain/event-storming.md:153-170`; `src/main/java/com/codeja/master_acdc/ordering/application/ConfirmOrderService.java:35-60`].

## Recorrido paso a paso

Las rutas de código siguientes son relativas a `src/main/java/com/codeja/master_acdc/`.

1. **Antes de confirmar: se crea el pedido y se reserva stock.** `CreateOrderService` construye un pedido `PENDING`, solicita la reserva a Inventario y solo lo guarda si se consigue. Si falta stock o el producto es desconocido, devuelve un error en vez de guardar el pedido. Esta es una **reserva lógica**, no el apartado físico en almacén.  
   **Fuentes:** `ordering/application/CreateOrderService.java:27-47`; `ordering/domain/model/Order.java:35-48`; `docs/domain/event-storming.md:230-235`.

2. **El cliente confirma la compra.** La entrada HTTP es `POST /api/orders/{id}/confirmation`. El servicio busca el pedido por identificador y cliente, y el agregado solo permite iniciar la confirmación si está `PENDING`; entonces pasa a `PAYING`.  
   **Fuentes:** `ordering/infrastructure/adapters/in/web/OrderConfirmationController.java:17-20`; `ordering/application/ConfirmOrderService.java:35-43`; `ordering/domain/model/Order.java:96-101`.

3. **Se fija el importe.** Si ya había un importe fijado en un intento anterior, se reutiliza. Si no, Pedidos consulta los precios de Catálogo mediante `CatalogPrices` y calcula el subtotal con el modelo compartido de Precios. El adaptador registra el intento y conserva el primer importe fijado. El cupón todavía **no llega al checkout**.  
   **Fuentes:** `ordering/application/ConfirmOrderService.java:44-46`; `ordering/infrastructure/adapters/out/catalog/CatalogOrderAmountCalculator.java:26-41`; `ordering/infrastructure/adapters/out/persistence/OrderPaymentJdbcAdapter.java:38-63`; `docs/domain/event-storming.md:234-239`.

4. **Se solicita la autorización a la pasarela externa.** El adaptador envía el importe a `/authorizations`, con una clave de idempotencia basada en el pedido y el número de intento. En el modelo actual, la autorización hace de cobro: **no existe un paso separado de captura**.  
   **Fuentes:** `ordering/application/ConfirmOrderService.java:47-49`; `ordering/infrastructure/adapters/out/payment/RestPaymentGateway.java:23-38`; `docs/domain/event-storming.md:236-237`.

5. **Resultado.**
   - Si se autoriza, `Order.registerPayment()` cambia el agregado a `PAID` y acumula `OrderConfirmed`. El adaptador persiste `PAID` y publica los eventos pendientes en la misma transacción. Ese es el punto en que el pedido queda confirmado.  
     **Fuentes:** `ordering/domain/model/Order.java:103-108`; `ordering/infrastructure/adapters/out/persistence/OrderPaymentJdbcAdapter.java:85-104`.
   - Si se rechaza, o hay timeout o indisponibilidad, el intento se abandona y el pedido vuelve a `PENDING`, conservando el importe. El contador de intento aumenta para un rechazo, pero no para timeout o indisponibilidad.  
     **Fuentes:** `ordering/application/ConfirmOrderService.java:48-57`; `ordering/infrastructure/adapters/out/persistence/OrderPaymentJdbcAdapter.java:66-82`.

6. **Después de confirmar, se actualiza Catálogo.** Un relay procesa la outbox de confirmaciones y llama a `CatalogStockProjection` para sincronizar los productos afectados. Por tanto, la disponibilidad visible puede ir por detrás de la confirmación; no es un paso previo para que el pedido quede `PAID`.  
   **Fuentes:** `ordering/infrastructure/adapters/out/persistence/OrderConfirmationRelay.java:19-38`; `docs/adr/0014-integracion-entre-contextos.md:35-40`.

### Reglas generales y excepciones

- **No debe haber ciclos.** Un módulo solo puede usar el paquete publicado de otro, y solo desde infraestructura; la excepción de Precios es su kernel compartido. Las consultas entre contextos van por esos puertos. Los efectos sobre otro contexto deben producirse mediante eventos. **Fuentes:** `docs/domain/context-map.md:85-108`; `docs/adr/0014-integracion-entre-contextos.md:18-24`.
- **No se accede a la persistencia ajena** —tablas, colecciones, entidades, documentos o repositorios—. Hay tres excepciones catalogadas: la reserva síncrona `InventoryFacade.reserve`, la llamada de Pedidos a `CatalogStockProjection` y la lectura de la tabla `stock` de Inventario desde Catálogo. Las dos últimas son deuda, no patrones a extender.
