# Design

## Context

La aplicación tiene un único `PlatformTransactionManager`, asociado a JPA, y la ficha se construye actualmente como `TransactionTemplate` alrededor del servicio. No hay `MongoTransactionManager`: las escrituras Mongo son inmediatas y no participan de la transacción JPA. La proyección de stock pagina productos por lotes y hace una actualización bulk, pero no distingue qué valores cambiaron. Además, el job no está registrado en configuración y no hay scheduling habilitado. Véanse `proposal.md` y los deltas de `product-detail` y `product-editing` para los contratos.

## Goals / Non-Goals

**Goals:** aplicar cache transparente solo a la lectura de ficha; invalidar ambas capas y propagar invalidaciones entre instancias; conservar resiliencia ante el almacén compartido caído; programar la sincronización de stock.

**Non-Goals:** cambiar contratos HTTP, cachear lecturas adicionales, alterar dependencias, propiedades de aplicación protegidas o configurar pruebas de carga.

## Decisions

- **Decorador de infraestructura exterior a la transacción.** `ProductConfiguration` construye el caso de uso de origen con el `TransactionTemplate` y envuelve ese bean con el decorador cacheado. Los hits retornan antes de ejecutar el delegado y por ello no abren transacción. La anotación aplica solo a la operación de ficha, nunca a reseñas.
- **Cache compuesta de dos niveles.** Una implementación de `Cache` consulta Caffeine primero y Redis después; los hits del segundo nivel se copian a L1 y los misses cargan y escriben en ambos. Un fallo de Redis al leer o escribir se registra y se trata como miss; un error de L1 no se oculta. Un `CacheManager` configura la pareja con los TTL de `docs/caching.md`. Para evitar colisiones, L1 y L2 se registran con nombres distintos (`products.l1` y `products.l2`) en Actuator y exponen métricas `cache.gets` independientes; la cache compuesta no se registra como un tercer nivel.
- **Serialización de Redis.** JSON tipado específicamente para `products`, limitado al valor `ProductDetail`, usando serializadores Jackson 3 de Spring Data Redis 4. Se usa el prefijo `shop:cache:v1:` y `clear` recorre claves mediante SCAN. No se admiten valores nulos; el error de producto inexistente se propaga sin almacenar valor.
- **Jitter y stampede.** TTL de Caffeine usa `Expiry` para creación y actualización; Redis calcula cada vencimiento mediante `TtlFunction`. Ambos aplican ±10%. La carga sincronizada impide que llamadas concurrentes de una instancia dupliquen el loader; no se pretende bloqueo distribuido entre instancias.
- **Invalidación y transacción.** `EditProductService` usa un puerto de salida equivalente al patrón de publicación existente. La escritura Mongo se hace inmediatamente y no participa en la transacción JPA. Tras el save exitoso, el servicio publica `ProductChanged(sku)` dentro del `TransactionTemplate`; el listener `AFTER_COMMIT` se dispara al terminar esa transacción del único `PlatformTransactionManager` (JPA), cuando la escritura Mongo ya es durable. No se presenta esta transacción como coordinadora de Mongo ni se añade un segundo gestor.
- **Evict y propagación aunque falle L2.** El listener intenta invalidar L2 tres veces con backoff corto. Si los tres intentos fallan, registra el error e incrementa un contador de evicts fallidos; aun así invalida L1 local y publica `cache|key|instanceId` por `shop:cache:evictions`. Los otros nodos eliminan su L1 al recibirlo e ignoran los mensajes propios. No se aplica `transactionAware()` únicamente a L2: el listener es el mecanismo común de invalidación.
- **Identidad de instancia.** La propiedad `cache.instance-id` identifica cada emisor de invalidaciones. Si no está configurada, se genera un UUID en código al arrancar; las pruebas multi-contexto fijan un valor diferente por contexto para verificar que cada instancia ignore solo sus propios mensajes.
- **Scheduler de stock.** La infraestructura habilita scheduling y registra el job de proyección solo cuando `catalog.stock-sync.enabled` es `true`, con `matchIfMissing = true` para mantenerlo habilitado por defecto. En tests se desactiva globalmente en `src/test/resources/config/application.properties`, que Spring Boot carga además del archivo de main y con prioridad, conservando `auto-index-creation=false` y la configuración de Redis. El test de programación activa explícitamente la propiedad.
- **Stock modificado sin romper lotes.** En cada lote, leer además de `_id` el `availableStock` previo; consultar disponibilidad en PostgreSQL una vez para todos los ids, comparar cada resultado (incluido cero cuando falta fila), preparar el bulk solo con valores que difieren y acumular los SKU afectados. Después de ejecutar correctamente el bulk, invalidar únicamente esos SKU. Se conserva el cursor y el tamaño de lote existentes, sin consultas por producto ni invalidaciones globales.
- **Fallos rápidos y errores de cache.** Redis tiene timeout de 200 ms y `ClientOptions` rechaza comandos mientras no hay conexión (`REJECT_COMMANDS`) en lugar de encolarlos. Un `CacheErrorHandler` registra errores de Redis como miss y deja que la aplicación cargue la ficha desde origen.
- **Reglas de arquitectura para ArchUnit:**
  - `catalog.domain` no depende de Spring, Redis, Caffeine ni Jackson.
  - `catalog.application` depende solo de `catalog.domain`, y no de infraestructura ni de APIs de cache.
  - `ordering` e `inventory` no dependen de la cache del catálogo ni del caso de uso cacheado de ficha.
  - Métodos anotados con `@Cacheable` no devuelven documentos Mongo ni tipos anotados como `@Entity`; solo records/modelos inmutables apropiados.
  - La configuración, adaptadores de cache, job programado y listeners quedan en `catalog.infrastructure`.
- **Pruebas Spring existentes.** `src/test/resources/config/application.properties` define `catalog.stock-sync.enabled=false` y `catalog.cache.enabled=false`; Spring Boot la carga además de las propiedades de main y con prioridad. No se crea `src/test/resources/application.properties`, que reemplazaría a las propiedades de main en el classpath. La configuración de cache compuesta (incluidos `CacheManager`, listener de invalidaciones y contenedor de mensajes) se registra con `@ConditionalOnProperty(catalog.cache.enabled, matchIfMissing = true)`. Cuando la cache está desactivada se proporciona un `NoOpCacheManager`, de modo que `@Cacheable` siga operando sin Redis. Los tests de cache y el test de programación activan explícitamente la propiedad que necesitan en sus propiedades de `@SpringBootTest`. Los contextos multi-instancia construidos con `SpringApplicationBuilder` pasan las propiedades requeridas como argumentos de línea de comandos a `run(...)` (`--catalog.cache.enabled=true`, `--cache.instance-id=...` y `--catalog.stock-sync.enabled=false`), con prioridad superior a las propiedades de test. Los guardianes `StockReservationConcurrencyTest`, `StockReservationTransactionIT` y `CatalogProductEditingMongoIT` no se modifican; permanecen bajo la configuración global de test. La integración de dos instancias usa Redis y Mongo compartidos, y un `cache.instance-id` distinto por contexto.

## Risks / Trade-offs

- **Pérdida de pub/sub durante reconexión** → el TTL de L1, como red de seguridad, caduca en no más de 16,5 s, por debajo del máximo de 30 s.
- **Evict de L2 fallido con Redis inestable** → la L2 podría conservar el valor viejo hasta su TTL (10 min) y repoblar L1. Tres intentos con backoff corto, contador y log hacen visible el fallo; invalidar L1 local y publicar a los demás nodos se completa aunque L2 falle. Este riesgo y su mitigación respetan el ADR 0010; no se relajan TTL ni se devuelve 5xx.
- **Fallo de commit JPA tras el save Mongo** → Mongo ya contiene el cambio aunque el evento `AFTER_COMMIT` no se dispare si la transacción JPA aborta. El save se realiza antes de publicar el evento dentro del `TransactionTemplate`; no hay atomicidad distribuida. Verificar el orden y este comportamiento en integración, sin presentar JPA como gestor de la escritura Mongo ni añadir otro transaction manager.
- **Serialización incompatible tras cambios de forma** → subir el prefijo de versión de cache cuando cambie `ProductDetail`.
- **Job que invalida antes de completar el bulk** → acumular los SKU cambiados por lote y emitir invalidaciones solo después de que el bulk termine con éxito.

## Migration Plan

No hay migración de datos ni cambio HTTP. Desplegar la configuración de Redis y la cache en las instancias; durante despliegue, la tolerancia de 200 ms limita el impacto de Redis indisponible. Para rollback, retirar la capa decoradora y listeners, conservando los datos fuente: las entradas del prefijo versionado caducan o pueden borrarse sin afectar Mongo.
